# Bluetooth ownership

`MiniAppBluetoothCoordinator` routes CoreBluetooth central work by `MiniAppID`. Each owner receives a distinct `CBCentralManager`, restoration identifier, scan, peripheral table, delegate lifetime, and connection generation. Two Features may connect to the same physical peripheral; stopping A only invokes A's manager and never calls `cancelPeripheralConnection` on B's manager.

Create one `MiniAppBluetoothService` per Feature and connect it from `MiniAppFeatureLifetime.configure`. Runtime shutdown closes the owner lease and callback delivery first, requests native cancellation, then waits for CoreBluetooth's disconnect/failure (or a terminal power transition). A replacement connection starts only after that join. Discovery objects are tagged with their native generation; callbacks from old services or characteristics are discarded. An older service instance cannot unregister a newer lease for the same owner.

Owner stop and per-peripheral reconnect each have a serialized transition barrier. A new lifetime lease waits for the previous owner's `stopAll` join, and concurrent reconnect requests become an ordered sequence rather than overwriting one another. If runtime cleanup registration fails (for example, an already-closed runtime), the newly created lease and manager are fully rolled back before the error escapes.

Call `prepareRestoration(admitted:onRestore:)` synchronously from `MiniAppDefinition.onHostLaunch`, after persisted management and Feature consent have both admitted the owner. Do not construct a manager for a disabled, denied, or removed owner. A cold restored snapshot is retained until `onRestore` starts the same Feature lifetime and installs its consumer. Connecting/restored peripherals are not reported as connected until CoreBluetooth says they are connected; disconnected restored objects are not adopted. Removal awaits `unregisterAllOwned()` after management has closed admission and joined lifetime shutdown.

The host must declare `bluetooth-central` in `UIBackgroundModes` when background discovery, connection events, or restoration are required. Add an appropriate Bluetooth usage description (`NSBluetoothAlwaysUsageDescription`; deployment-target requirements should be checked against the shipping SDK). Restoration is not a durable business-data store: persist application intent separately, and do not silently restart removed owners.

The adapter keeps `CBPeripheral`, `CBService`, and `CBCharacteristic` objects for the life of their owner generation. Advertisement local name, manufacturer bytes, service-data bytes, UUID lists, TX power, and connectability are copied without string flattening. A write is rejected when it exceeds CoreBluetooth's maximum length; without-response writes also require `canSendWriteWithoutResponse`, and retry is signaled by `readyToWriteWithoutResponse`. Direct CoreBluetooth use remains possible for device-specific protocols.

GATT permits multiple service instances with the same UUID. The portable UUID-only API reports every discovered UUID but refuses characteristic discovery when that UUID is ambiguous, instead of crashing or silently selecting an instance. A device protocol that needs duplicate service instances needs an alternative native adapter with its own CBService instance selector, managed by the same Feature runtime/cleanup contract. The current adapter retains these objects privately and does not expose them for direct access; this is a JibunKit API limitation, not an OS or signing restriction.

## Verification boundary after 0.8.4

Device source `fe1a6e5` verified single-owner read/write/notify, notification delivery to both owners on one Android peripheral, Sensor disable while Accessory remained operational, and reception after scan stop and explicit disconnect/reconnect. Notifications were sent while ChatGPT was foreground on the iPhone and inspected after returning; callback execution specifically in background was not timestamped. The earlier dual-owner failure did not reproduce after the fix, but its original internal cause remains unconfirmed.

Source `7e4c740`, CI35325946663, verified the combined native73/shared24 suites and IPA. The restored GATT graph is indexed with its native object identities before connection admission. Events that arrive before the Feature consumer are retained in order, up to 256 entries; overflow replaces the last entry with an explicit failure requiring state reconciliation. A truncated stream is not reported as complete. These tests do not exercise an OS cold-restoration launch.

Diagnostic source `59f7081` subsequently exercised real OS state restoration in a new process. The device log at 2026-09-18T12:56:16Z contains `willRestoreState`, restored connection and a two-byte notification on the same owner/connection generation before consumer setup completed. Later process starts contained restored connections without a recorded matching notification; they do not invalidate the earlier observation. The log does not identify whether launch was automatic in background or caused by manual app entry, nor does it persist the notification payload. OS background wake, reboot, and power/authorization transitions remain separate unobserved conditions. Deterministic stale-generation, cancellation, and management cases belong in automated regression, rather than a repeated full manual matrix. The real-device result is scoped to the tested peripheral and source, not every firmware or protocol.

Use `try await service.connect(to: runtime)` in the lifetime configure closure. A restored `connected` event is delivered after the service installs its lease and runtime; inside that callback, `try service.currentConnection(peripheral:)` retrieves the current owner ticket for discovery/read/write/subscribe. A ticket does not itself prove physical connection readiness: use the connected event. Closed or replaced leases reject lookup; explicitly disconnected peripherals return nil.

P2-9's adopted ordinary scope is complete based on the device evidence above and source `1138ded` / CI35352655988 native regression. The latter includes persistent historical evidence selection and rejection of a normal reconnection notification as restoration. That CI's unrelated two-window UI failure does not erase these passing native results. Automatic OS wake and bounded wake latency remain unproven and are not promised. These development results do not change the public 0.8.4 binary.
