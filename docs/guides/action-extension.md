# Purpose-limited Action Extension

JibunKit's Action Extension is an optional, adopted configuration for receiving an item from another app. It presents the same owner-scoped inbox admission flow as the Share Extension, copies the selected input into the chosen mini-app's durable inbox, and completes with an empty returned-items array. It does not edit the source item or produce a transformed document.

This target is intentionally not part of every normal build. Set `EnabledFeatureBuildRequirements.action` to `FeatureBuildConfiguration()` (or a configuration with the host requirements) to enable the supplied Tuist target. The default `nil` omits it. Tuist adds the distinct target and signing identifier, compiles `Sources/JibunKitIncomingExtensionUI/MiniAppIncomingExtensionViewController.swift` and `Sources/JibunKitAction/ActionViewController.swift` into that target, links `JibunKitCore`, embeds the extension, and uses the same App Group entitlement as the host. Hosts with a custom identifier must keep the group and bundle identity aligned. The Share target likewise compiles the shared controller plus its existing thin `ShareViewController` entry.

Configure the Action target's extension point as `com.apple.ui-services`, set `NSExtensionPrincipalClass` to the target-qualified `ActionViewController`, and use activation rules limited to the input types the host intends to accept. Keep the Share target on `com.apple.share-services`; the two entries have separate titles, guidance, and accessibility identifiers even though their durable-save implementation is shared.

Completion means that `MiniAppIncomingStore.enqueue` has committed a receipt after rechecking the selected owner's admission. Cancellation joins any provider/copy task before temporary files are released, then calls `cancelRequest`. A successful request calls `completeRequest(returningItems: [])`, because this example is a save action rather than an editing action.

Validate the actual system Action entry on a physical device with representative input and one cancellation; reuse shared text/URL/file decoding evidence where the implementation is identical, then confirm selected-owner delivery and other-owner preservation. Provider-load/copy cancellation races, temporary cleanup, and admission changes during saving belong to deterministic automatic tests; do not require users to time these races manually. Also verify the Action entry itself in the system action sheet. Share fixtures or Share Extension coverage do not prove that the Action Extension is discoverable or launched by iOS.

This is an incoming-save example and a basis for a host-specific Action Extension. Arbitrary native screens or arbitrary actions are not automatically exposed through it. A Notification Service Extension is also unnecessary for ordinary APNs delivery; if a product later needs notification payload mutation or attachment download, that is a separate extension design and lifecycle decision rather than something completed merely by omitting `mutable-content`.

Action and Share use the same item-provider loading, input decoding, durable enqueue, and cancellation implementation; their entry subclass differs in presentation. Existing physical Action URL/file entry evidence, physical Share text evidence, and native text/provider tests therefore cover the adopted input path without requiring another manual text-only Action run or two additional IPA installations. The adopted P2-13 save-only Action scope is complete; arbitrary extension integration and other mandatory P2 extensions are not implied.
